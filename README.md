# 地方競馬AI (南関東4場+門別・盛岡・金沢・名古屋・園田・高知・佐賀 計11場)

地方競馬11場の実データで学習したAIモデルと、netkeibaからの自動スクレイピング&予想パイプラインです。

## 構成

```
.
├── model/
│   ├── model_nar11_is_win.txt         # 単勝勝率モデル(LightGBM・9場対応)
│   ├── model_nar11_is_top3.txt        # 複勝(3着内)率モデル(LightGBM・9場対応)
│   ├── predict.py                      # スクレイピング済みデータ→予想結果CSV
│   └── generate_dashboard.py           # 予想結果→貼り付け不要のHTMLダッシュボード
├── scraper/
│   ├── scraper_netkeiba.py            # 出馬表スクレイパー(Playwright)
│   ├── rescrape_near_deadline.py      # 締切間近レースだけの再取得(オッズ更新)
│   └── shutuba_past_parser.py         # 出馬表テキストの解析ロジック
├── tools/
│   ├── keiba_ai_predictor.html        # ブラウザ版予想ツール(全場・門別など)
│   └── keiba_ai_predictor_nar11.html          # ブラウザ版予想ツール(9場対応)
├── .github/workflows/
│   ├── scrape_and_predict.yml         # 毎日07:00 JSTに自動実行するActionsワークフロー
│   └── rescrape_near_deadline.yml     # 締切間近(10分おき)のオッズ更新ワークフロー
└── requirements.txt
```

## データソースについて(重要・必読)

**keiba.go.jp(地方競馬情報サイト)はrobots.txtで自動アクセスを禁止しています。** 対象にしないでください。

**netkeiba(nar.netkeiba.com)は自動アクセスを禁止していません**(2026年8月時点でfetchツールで確認)。
ただし変更される可能性があるため、本番運用前に `https://nar.netkeiba.com/robots.txt` と
利用規約を必ず確認してください。

`race/shutuba_past.html?race_id=XXX` を使っています。プレミアム会員でなくても全頭分の
直近5走詳細(日付・クラス・距離・タイム・馬場状態・頭数・人気・騎手・斤量・馬体重・
上がり3F・通過順・着差)が取得できるためです。

## モデルについて(2026年8月・オッズ対応版)

### 発見した問題と対応

以前のモデルは「オッズを使わない」設計でしたが、2025年1月〜2025年12月の南関東4場・実際の
払戻データで検証したところ、**AIモデルの本命(単勝的中率25.7%)が、何もせず市場の1番人気を
買うだけの場合(単勝的中率43.4%)に負けている**ことが判明しました。市場オッズには騎手・
調教師の意図など、モデルが持っていない情報が織り込まれているためと考えられます。

このため、**現在レースの「人気」(オッズ由来)をモデルの入力特徴量に追加**しました。

### 学習データと検証結果

- 2025年1月〜2026年7月の南関東4場データで学習(通算成績・距離・コース種別・通過順は
  `shutuba_past.html`では取得できないため特徴量から除外し、学習/本番の条件を一致させています)
- 検証: 2025年11-12月を完全ホールドアウトとし、**実際の払戻金**でROIを検証
  - 単勝的中率 43.3%(市場の1番人気 43.4%とほぼ同水準)
  - 複勝的中率 76.0%、複勝回収率 89.9%(市場の74.3%/88.9%をわずかに上回る)
- 参考: オッズ特徴量を追加する前の旧モデルは単勝的中率25.7%、複勝的中率51.7%でした

### 9場対応版(`model_nar9_*`)への拡張

門別・盛岡・金沢・名古屋・園田・高知・佐賀の7場のデータ(2025.csvと同形式)を追加して、
南関東4場と合わせた計11場・約12.6万件で再学習しました。

- **検証方法の違い(正直な注意点)**: 新5場のデータには日付情報が含まれていなかったため、
  南関東4場のような時系列ホールドアウト検証ができず、**ランダム分割での検証**になっています
  (南関東4場側は既に時系列検証済みの実績があります)。ランダム分割AUC: 単勝0.854 / 複勝0.820
- 場所ごとのAUCも個別確認済み(0.81〜0.93、サンプル数の少ない園田はやや不安定)
- **オッズ・出走馬情報を含まない特徴量(通算成績・距離・コース種別)は引き続き未使用**です

### 締切間近レースのオッズ更新(`rescrape_near_deadline.yml`)

**オッズが主要因子になったため、この再取得は表示更新ではなく予測精度そのものに直結します。**
`.github/workflows/rescrape_near_deadline.yml` が**10分おき(12:00〜22:00 JST)**に、
発走10分前以内のレースだけを狙って再取得し、最新のオッズ/人気で予想・ダッシュボードを
再生成します。

**正直な制約**:
- GitHub Actionsのスケジュール実行は、指定時刻ちょうどに動く保証がありません
  (公式にも「遅延することがある」と明記されており、数分〜十数分ズレることがあります)。
  「締切10分前ぴったり」を保証するものではなく、あくまで「近いタイミングで」の更新です
- 実行頻度を上げるほどGitHub Actionsの無料実行時間を消費し、netkeibaへのアクセス頻度も
  上がります。不要な場合は `rescrape_near_deadline.yml` を削除するか、cronをコメントアウト
  してください
- 深夜0時をまたぐレース(通常の南関東開催時間外)には対応していません

## 使い方(ローカル)

```bash
cd scraper
python scraper_netkeiba.py --date 2026-08-14

cd ../model
python predict.py --input ../scraper/scraped_data/2026-08-14_racecards_raw.jsonl
python generate_dashboard.py --date 2026-08-14
```

**注意**: Jupyterノートブックのセルに直接貼り付けて実行すると、Playwrightの同期APIが
非同期イベントループと競合してエラーになります。ターミナル/コマンドプロンプトから
`python scraper_netkeiba.py` の形で実行してください。

## GitHub Actionsでの自動化

`.github/workflows/scrape_and_predict.yml` が毎日07:00 JSTに自動実行し、`scraper/scraped_data/`
に生データとCSVを、`docs/` に**貼り付け不要で見られる予想ダッシュボード**をコミットします。
手動実行(Actionsタブ→Run workflow)も可能です。

### ダッシュボードをGitHub Pagesで公開する(推奨)

1. リポジトリの Settings → Pages を開く
2. Source を「Deploy from a branch」、Branch を `main` / `/docs` に設定して保存
3. 数分後、`https://{ユーザー名}.github.io/{リポジトリ名}/` で毎朝自動更新される
   予想一覧が見られるようになります(貼り付け操作は一切不要です)

失敗時は最初のリクエストのスクリーンショットが `debug-screenshots` アーティファクトとして
保存されるので、実行結果ページ下部から確認できます。

## 正直な現状・今後の課題

1. **オッズの鮮度**: 上記「重要なトレードオフ」の通り、朝1回の取得だと発走直前のオッズ変動を
   捉えられません。より高精度を狙うなら締切間近の再取得が有効です
2. **通算成績・距離・コース種別・通過順は特徴量として使っていません**。`shutuba_past.html`
   では取得できないためです。将来的にこれらを取得できる別ページと組み合わせられれば、
   さらなる精度向上の余地があります
3. **レース格・距離の抽出精度**: `predict.py` の `guess_race_meta()` は正規表現による簡易抽出
   です(表示用のみで、モデルの入力には使っていません)
4. **バックテストの限界**: 2025-2026年のバックテストは`horselist`/`payback`CSVを元にしており、
   `shutuba_past.html`とは微妙にデータソースが異なります(例: 頭数情報が無いため
   `avg5_headcount`は使えていません)。本番運用での実際の的中率は、多少変動する可能性があります
